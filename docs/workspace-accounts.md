# 제작자·운영자·참가자 분리 — v5.2.0

이번 버전은 각 Discord 서버가 각자의 카페·CHZZK 방송 채널을 운영하는 구조를 추가합니다. `MULTI_WORKSPACE_ENABLED=false`가 기본값이며, 기존 단일 운영 방식과 기존 데이터를 유지합니다. 실제 계정 E2E를 마치기 전에는 공개 서비스를 활성화하지 않습니다.

## 계정과 화면

| 사용자 | 로그인 | 사용할 화면 | 허용 범위 |
|---|---|---|---|
| 제작자 | 기존 관리자 이름·비밀번호 | `/`, `/creator/` | 전체 배포·진단·릴리스·복구 및 서버별 점검 |
| 방송 운영자 | Discord OAuth | `/portal/` | 현재 Discord에서 소유자 또는 서버 관리 권한이 있는 서버의 방송 운영 |
| 참가자 | Discord OAuth | `/portal/` → 내 참가 상태 | 본인 신청·호출 응답·예약·준비·문의 |

운영자도 참가자 화면에서는 자신의 정보만 확인합니다. Discord 서버 관리 권한은 제작자 권한을 부여하지 않습니다. 기존 `DASHBOARD_OPERATOR_*`는 제작자의 기존 위임 계정이며 일반 배포 사용자에게 공유하지 않습니다.

화면은 통합 운영 / 네이버 카페 / Discord / CHZZK 대분류와 중분류·개별 기능으로 나뉩니다. 선택한 분류만 펼쳐집니다. 모바일은 메뉴 버튼으로 접습니다. 봇 점검·환경변수·배포·복구 메뉴와 API는 일반 사용자에게 허용하지 않습니다.

## 제작자 설정

기존 `.env`와 데이터, 토큰 암호화 키를 유지합니다. 새로 필요한 값은 아래 둘입니다.

```dotenv
# 실제 Discord OAuth Client Secret은 Railway Variables에만 저장
DISCORD_CLIENT_SECRET=
# 검증 전에는 false 유지
MULTI_WORKSPACE_ENABLED=false
```

1. 기존 Discord 애플리케이션의 OAuth2 Redirects에 `https://api-production-06643.up.railway.app/portal/auth/callback`을 등록합니다. 별도 호스트를 사용하면 해당 공개 origin으로 바꿉니다.
2. Client Secret을 Railway `api` 서비스의 `DISCORD_CLIENT_SECRET`에 저장합니다. Bot Token과 다른 값입니다. 채팅·Git·스크린샷에 포함하지 않습니다.
3. `PUBLIC_BASE_URL`은 실제 루트 HTTPS 주소, `TRUST_PROXY_HOPS`는 호스트의 실제 프록시 홉 수로 설정합니다. 포털 콜백은 코드에서 위 경로로 고정합니다.
4. CHZZK 앱 콜백은 동일 origin의 `/oauth/chzzk/callback`, 네이버 앱 콜백은 `/naver/callback`을 사용합니다. `NAVER_TOKEN_KEY`와 `CHZZK_TOKEN_KEY`는 변경하지 않습니다.
5. `DISCORD_GUILD_ID`는 기존 제작자 방송 서버를 나타냅니다. 새 서버마다 Railway 변수를 추가할 필요가 없습니다.
6. 공개 전 아래 E2E를 별도 검증 환경에서 완료한 다음 `MULTI_WORKSPACE_ENABLED=true`로 활성화합니다.

Discord 로그인 scope는 `identify guilds`이며 이메일을 수집하지 않습니다. OAuth access/refresh token은 디스크와 로그인 세션에 저장하지 않습니다. 로그인은 최대 8시간이며 서버 재시작 시 다시 로그인합니다. 봇 초대는 채널 관리, 닉네임 관리, 역할 관리, 채널 보기, 메시지 보내기, 링크 임베드, 메시지 기록 읽기를 요청합니다. Administrator 및 신규 Privileged Intent는 요청하지 않습니다. 역할 부여 대상은 봇 역할보다 아래에 있어야 합니다.

## 방송 운영자의 첫 사용

1. `/portal/`에서 Discord로 로그인합니다.
2. 봇이 입장한 자신의 서버를 선택하고 운영 공간을 만듭니다. 현재 Discord 권한을 확인하므로 타인의 서버를 만들거나 관리할 수 없습니다.
3. Discord → 서버 운영 → 서버 채널 준비를 실행합니다. 채널 생성·안내 게시는 이 명시적 버튼으로 실행합니다.
4. CHZZK → 방송 계정 → 방송 계정 연결에서 **해당 방송 소유자**로 동의합니다. 제작자의 방송 채널을 자동으로 복사하지 않습니다.
5. 카페 운영이 필요하면 네이버 계정을 연결하고 카페·게시판 ID를 저장합니다. 봇이 카페에 게시할 수 있는 실제 권한이 필요합니다.
6. 팔로워 인증 안내를 게시하고 참가자는 각자의 Discord·CHZZK 계정으로 인증합니다. 계정 비밀번호를 운영자에게 제공하지 않습니다.

서버별 연결은 서로 다른 방송을 구분하기 위해 처음 한 번 필요합니다. 이후에는 서버별 저장된 설정을 사용하며 매번 환경변수를 입력하지 않습니다.

## 저장·복구·배포

기존 제작자 파일은 원래 경로에 유지됩니다. 신규 공간은 `dirname(OPERATIONS_FILE)/workspaces/<guildId>/`에 저장됩니다. registry도 같은 `workspaces` 폴더에 있습니다. 서버별 Queue, 참가자, operations, 카페/CHZZK 암호화 토큰, 호출·알림, idempotency, 백업을 분리합니다. OBS 접근 토큰도 서버마다 다릅니다.

Railway의 `/app/data` 영구 볼륨을 유지하고 **`/app/data` 전체**를 백업해야 합니다. 기존 `data/backups`만 복사하면 신규 서버들의 파일은 포함되지 않습니다. 서버별 복원 지점은 Queue 등 기존 복구 설계의 범위를 따릅니다. 토큰 파일·registry까지 복구하는 재해 복구에는 전체 볼륨 백업과 원래 암호화 키가 필요합니다.

이 버전은 JSON 파일을 사용하는 단일 프로세스 운영입니다. Railway replica는 1로 유지하고 같은 볼륨을 여러 프로세스가 동시에 쓰게 하지 않습니다. 초기 등록 상한은 제작자 공간을 포함하여 최대 25개입니다. 대규모 공개 전에는 부하 측정과 저장소 확장 검토가 필요합니다.

```sh
npm ci
npm run env:check
npm run verify:final
npm start
```

Node >=22.22.2가 필요합니다. `/healthz` 200, 재시작 후 Queue 복구, 전체 잠금 시 모든 공간의 외부 전송 중단을 확인합니다. 종료 중인 요청·호출·알림을 기다린 뒤 파일을 flush합니다. 종료 대기 시간 초과 시 정상 종료로 표시하지 않습니다. 한 공간의 손상은 다른 공간 시작을 막지 않으며 제작자에게 점검 상태를 표시합니다.

`MULTI_WORKSPACE_ENABLED=false`로 되돌리면 포털을 내리고 기존 운영 방식으로 돌아갑니다. 신규 서버 파일은 보관됩니다. 코드 롤백 시에도 볼륨과 키를 유지해야 하며 신규 서버들의 호출·알림 운영이 중단된다는 점을 확인합니다. 자동 롤백/업데이트는 코드만 다루며 운영 볼륨 백업을 대신하지 않습니다.

## 실제 계정 E2E — 아직 PENDING

로컬 가상 API 테스트 통과는 실제 OAuth·Discord 권한·카페 쓰기 권한을 증명하지 않습니다. 공개 활성화 전에 다음 표를 실제 검증 기록으로 채웁니다.

| 순서 | 확인 내용 | 기대 결과 |
|---|---|---|
| 1 | 제작자 로그인, 운영자/참가자의 제작자 API 접근 | 제작자만 허용, 나머지는 403 |
| 2 | 서버 A·B 운영자가 서로의 URL에 접근 | 현재 회원/서버 관리 권한에 따라 차단 |
| 3 | A·B의 서로 다른 CHZZK 방송 소유자 연결 | 인증 대상이 각 서버에만 반영 |
| 4 | 참가자 별도 계정의 팔로우/미팔로우 인증 | 성공 시 해당 서버의 인증 역할만 부여, 미팔로우는 거절 |
| 5 | Discord 참가 → 카페 접수 → 통합 Queue | 각 서버의 순서에만 반영, 중복 정책 유지 |
| 6 | 호출 → 응답 → 노쇼 → 다음판/다다음판 | 본인 작업만 가능, 호출 상태 일관성 유지 |
| 7 | 준비 확인 → 추첨 → 팀 배정 → OBS | 해당 서버 참가자·결과만 표시 |
| 8 | 타 서버 OBS 토큰으로 접근 | 403, 올바른 서버 토큰은 허용 |
| 9 | 운영자 권한 제거/서버 탈퇴 후 조작 | 다음 쓰기 요청에서 차단, 읽기 캐시 최대 15초 |
| 10 | 긴급 잠금 → 서버 재시작 → 잠금 해제 | 외부 전송 중단, Queue·연결 파일 복구 |
| 11 | 방송 종료·기록 확인 → 전체 볼륨 백업 복원 | 두 서버 데이터·원래 키로 복구 |

현재 별도 참가자 계정이 없어 실제 팔로워 역할 부여 검증은 PENDING입니다. 검증을 위해 다른 사람의 인증정보를 수집하지 않습니다.

기존 제작자 대시보드의 고급 OBS 편집·Runbook·Preflight 등은 그대로 보존했습니다. 새 포털은 일상 방송 운영 중심입니다. 기존 고급 화면 전체를 일반 사용자에게 공개하는 것은 이번 배포의 범위가 아니며, 제작자 진단 API는 계속 차단합니다.
