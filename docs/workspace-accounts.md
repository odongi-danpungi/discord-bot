# 제작자·운영자·참가자 분리 — v5.2.7

v5.2.0의 계정 분리 기반을 유지하며 각 Discord 서버가 각자의 카페·CHZZK 방송 채널을 운영합니다. v5.2.7에서는 참가자 본인의 네이버 계정 소유 확인을 별도로 추가합니다. `MULTI_WORKSPACE_ENABLED=false`가 기본값이며, 기존 단일 운영 방식과 기존 데이터를 유지합니다. 실제 계정 E2E를 마치기 전에는 공개 서비스를 활성화하지 않습니다.

## 계정과 화면

| 사용자 | 로그인 | 사용할 화면 | 허용 범위 |
|---|---|---|---|
| 제작자 | 기존 관리자 이름·비밀번호 | `/`, `/creator/` | 전체 배포·진단·릴리스·복구 및 서버별 점검 |
| 방송 운영자 | Discord OAuth | `/portal/` | 현재 Discord에서 소유자 또는 서버 관리 권한이 있는 서버의 방송 운영 |
| 참가자 | Discord OAuth | `/portal/` → 내 참가 상태 | 본인 신청·호출 응답·예약·준비·문의 |

운영자도 참가자 화면에서는 자신의 정보만 확인합니다. Discord 서버 관리 권한은 제작자 권한을 부여하지 않습니다. 기존 `DASHBOARD_OPERATOR_*`는 제작자의 기존 위임 계정이며 일반 배포 사용자에게 공유하지 않습니다.

화면은 통합 운영 / 방송 / 네이버 카페 / Discord / CHZZK 대분류와 중분류·개별 기능으로 나뉩니다. 선택한 분류만 펼쳐집니다. 모바일은 메뉴 버튼으로 접습니다. 봇 점검·환경변수·배포·복구 메뉴와 API는 일반 사용자에게 허용하지 않습니다.

## 제작자 설정

기존 `.env`와 데이터, 토큰 암호화 키를 유지합니다. 새로 필요한 값은 아래 둘입니다.

```dotenv
# 실제 Discord OAuth Client Secret은 Railway Variables에만 저장
DISCORD_CLIENT_SECRET=
# 검증 전에는 false 유지
MULTI_WORKSPACE_ENABLED=false
```

1. 기존 Discord 애플리케이션의 OAuth2 Redirects에 `https://api-production-06643.up.railway.app/portal/auth/callback`을 등록합니다. 별도 호스트를 사용하면 해당 공개 origin으로 바꿉니다.
2. Client Secret을 Railway `api` 서비스의 `DISCORD_CLIENT_SECRET`에 저장합니다. Bot Token과 다른 값입니다. 채팅·Git·스크린샷에 포함하지 않습니다.
3. `PUBLIC_BASE_URL`은 실제 루트 HTTPS 주소, `TRUST_PROXY_HOPS`는 호스트의 실제 프록시 홉 수로 설정합니다. 포털 콜백은 코드에서 위 경로로 고정합니다.
4. CHZZK 앱 콜백은 동일 origin의 `/oauth/chzzk/callback`, 네이버 앱 콜백은 `/naver/callback`을 사용합니다. `NAVER_TOKEN_KEY`와 `CHZZK_TOKEN_KEY`는 변경하지 않습니다.
5. `DISCORD_GUILD_ID`는 기존 제작자 방송 서버를 나타냅니다. 새 서버마다 Railway 변수를 추가할 필요가 없습니다.
6. 공개 전 아래 E2E를 별도 검증 환경에서 완료한 다음 `MULTI_WORKSPACE_ENABLED=true`로 활성화합니다.

Discord 로그인 scope는 `identify guilds`이며 이메일을 수집하지 않습니다. OAuth access/refresh token은 디스크와 로그인 세션에 저장하지 않습니다. 로그인은 최대 8시간이며 서버 재시작 시 다시 로그인합니다. 봇 초대는 채널 관리, 닉네임 관리, 역할 관리, 채널 보기, 메시지 보내기, 링크 임베드, 메시지 기록 읽기를 요청합니다. Administrator 및 신규 Privileged Intent는 요청하지 않습니다. 역할 부여 대상은 봇 역할보다 아래에 있어야 합니다.

## 방송 운영자의 첫 사용

1. `/portal/`에서 Discord로 로그인합니다.
2. 봇이 입장한 자신의 서버를 선택하고 운영 공간을 만듭니다. 현재 Discord 권한을 확인하므로 타인의 서버를 만들거나 관리할 수 없습니다.
3. Discord → 서버 운영 → 서버 채널 준비를 실행합니다. 채널 생성·안내 게시는 이 명시적 버튼으로 실행합니다.
4. CHZZK → 방송 계정 → 방송 계정 연결에서 **해당 방송 소유자**로 동의합니다. 제작자의 방송 채널을 자동으로 복사하지 않습니다.
5. 카페 운영이 필요하면 네이버 계정을 연결하고 카페·게시판 ID를 저장합니다. 봇이 카페에 게시할 수 있는 실제 권한이 필요합니다.
6. 팔로워 인증 안내를 게시하고 참가자는 각자의 Discord·CHZZK 계정으로 인증합니다. 계정 비밀번호를 운영자에게 제공하지 않습니다.

서버별 연결은 서로 다른 방송을 구분하기 위해 처음 한 번 필요합니다. 이후에는 서버별 저장된 설정을 사용하며 매번 환경변수를 입력하지 않습니다.

## 저장·복구·배포

기존 제작자 파일은 원래 경로에 유지됩니다. 신규 공간은 `dirname(OPERATIONS_FILE)/workspaces/<guildId>/`에 저장됩니다. registry도 같은 `workspaces` 폴더에 있습니다. 서버별 Queue, 참가자, operations, 카페/CHZZK 암호화 토큰, 호출·알림, idempotency, 백업을 분리합니다. OBS 접근 토큰도 서버마다 다릅니다.

Railway의 `/app/data` 영구 볼륨을 유지하고 **`/app/data` 전체**를 백업해야 합니다. 기존 `data/backups`만 복사하면 신규 서버들의 파일은 포함되지 않습니다. 서버별 복원 지점은 참가자 등록·Operations를 담으며 Queue 파일·호출 설정·토큰·registry 전체를 포함하지 않습니다. v5.2.5의 패스 예약·결정은 Operations에, 해당 결정의 Queue 적용·자동 진행 기록은 Queue 파일에 있습니다. 재해 복구에는 서로 일치하는 전체 볼륨 백업과 원래 암호화 키가 필요합니다.

이 버전은 JSON 파일을 사용하는 단일 프로세스 운영입니다. Railway replica는 1로 유지하고 같은 볼륨을 여러 프로세스가 동시에 쓰게 하지 않습니다. 초기 등록 상한은 제작자 공간을 포함하여 최대 25개입니다. 대규모 공개 전에는 부하 측정과 저장소 확장 검토가 필요합니다.

```sh
npm ci
npm run env:check
npm run verify:final
npm start
```

Node >=22.22.2가 필요합니다. `/healthz` 200, 재시작 후 Queue 복구, 전체 잠금 시 모든 공간의 외부 전송 중단을 확인합니다. 종료 중인 요청·호출·알림을 기다린 뒤 파일을 flush합니다. 종료 대기 시간 초과 시 정상 종료로 표시하지 않습니다. 한 공간의 손상은 다른 공간 시작을 막지 않으며 제작자에게 점검 상태를 표시합니다.

`MULTI_WORKSPACE_ENABLED=false`로 되돌리면 포털을 내리고 기존 운영 방식으로 돌아갑니다. 신규 서버 파일은 보관됩니다. 코드 롤백 시에도 볼륨과 키를 유지해야 하며 신규 서버들의 호출·알림 운영이 중단된다는 점을 확인합니다. 자동 롤백/업데이트는 코드만 다루며 운영 볼륨 백업을 대신하지 않습니다.

## 참가자 네이버 계정 — v5.2.7 선택 기능

운영자의 카페 글쓰기 계정과 참가자의 개인 연결은 분리합니다. 참가자는 포털에서 현재 서버의 **내 참가 상태 → 내 네이버 계정**으로 이동해 수집 목적·범위를 확인하고 동의한 뒤 연결합니다. 운영자도 참가자 화면에서는 본인 연결만 조회·해제할 수 있습니다. 연결되지 않아도 기존 Discord 신청·호출·예약 기능은 유지하며, 이 연결을 참가 자격 필수 조건으로 추가하지 않습니다.

제작자는 참가자 로그인 전용 네이버 앱을 별도로 준비하고 다음 선택 변수를 서버 Secret 저장소에 입력합니다. 운영자 카페 앱 값을 자동 복사하지 않습니다.

```dotenv
NAVER_PARTICIPANT_CLIENT_ID=
NAVER_PARTICIPANT_CLIENT_SECRET=
# 기존 NAVER_TOKEN_KEY를 유지하며 값을 새로 만들거나 여기에 붙여넣지 않습니다.
```

참가자 앱의 Callback은 `PUBLIC_BASE_URL` origin + `/naver/participant/callback`입니다. 기존 운영자 앱의 `/naver/callback`과 혼동하지 않습니다. 참가자 앱은 계정 식별에 필요한 최소 프로필 권한으로 구성하고 이메일·이름·닉네임·생일·연락처 등 불필요한 제공 항목과 카페 가입·글쓰기 API를 추가하지 않습니다. 실제 등록 화면과 검수·동의 조건은 [네이버 로그인 개발가이드](https://developers.naver.com/docs/login/devguide/devguide.md)를 확인합니다. 앱의 공개 사용 가능 여부도 실제 서비스 E2E에서 확인해야 합니다.

두 값이 비었거나 일부만 있으면 참가자 연결 기능만 준비 전으로 표시하며 운영자 인증정보로 대신 연결하지 않습니다. 참가자 전용 설정이 있는 경우 기존 `NAVER_TOKEN_KEY`만으로 운영자 카페 앱을 켜지 않습니다. 기존 운영자 필드가 설정되어 있으면 운영자 앱의 기존 쌍 검증을 유지합니다. 설정한 키가 잘못된 HEX·Base64 형식이면 시작 단계에서 거절합니다. 정상 키도 임의 교체하지 않습니다.

콜백은 로그인 세션·본인·서버·revision·10분 일회용 state에 연결됩니다. 새 연결과 로컬 해제는 이전 진행 중 동의를 무효화하며, 네이버 응답 후에도 현재 Discord 멤버십과 저장 직전 운영 잠금을 다시 확인합니다. 조회는 본인 연결 요약만 반환하며 외부 API·자동 토큰 갱신·Queue 저장을 수행하지 않습니다.

연결 상태는 **당시 계정 소유 확인 기록**입니다. 네이버 앱별 식별값은 서로 다를 수 있으므로 운영자 앱·참가자 앱·CHZZK 계정이나 카페 접수 닉네임을 같은 사람으로 합치지 않습니다. 카페 회원·현재 닉네임·지속적인 외부 동의·팔로워 여부·참가 자격의 증명이 아니며 기존 Queue 순서·예약·추첨·역할을 바꾸지 않습니다. 네이버의 식별값 범위는 [회원 프로필 API 명세](https://developers.naver.com/docs/login/profile/profile.md)를 참조합니다.

서버별 `dirname(OPERATIONS_FILE)/participant-identities.json`에 `{version:1, revision, links}`를 보관합니다. 링크에는 Discord 사용자 ID, 서버·참가자 앱 범위 HMAC 식별값, 앱과 키 구분값, 연결 시각만 남습니다. 원본 네이버 ID·이름·이메일·프로필·OAuth access/refresh token은 영속화하지 않습니다. 기존 Operations 스키마 2는 바꾸지 않습니다. 연결 파일과 `.bak`·`.tmp` 복구 자료도 접근을 제한한 전체 볼륨 백업 범위에 포함합니다.

**연결 해제**는 로컬 기록과 진행 중 요청을 해제하며 네이버 측 동의를 철회하거나 토큰 삭제 API를 호출하지 않습니다. 외부 앱 동의 철회는 사용자가 네이버 계정 관리에서 별도로 확인해야 합니다. 로컬 해제 뒤 새 동의를 시작할 수 있습니다. 앱 또는 HMAC 키가 바뀌면 기존 연결을 새 앱·키의 계정으로 간주하지 않고 재연결을 안내합니다.

Operations 복원 지점은 별도 연결 파일을 포함하지 않습니다. 전체 `/app/data`와 기존 `NAVER_TOKEN_KEY`를 함께 보관하고 replica 1을 유지합니다. 이전 코드로 롤백하면 새 연결 파일을 무시하므로 파일을 보존합니다. 볼륨 복원으로 해제 전 과거 연결이 돌아올 수 있으며, 이 경우 참가자의 동의 의사·연결 해제 여부를 확인하고 필요한 재연결을 진행해야 합니다. 복원만으로 현재 외부 연결이 유효하다고 판단하지 않습니다. 자동 Queue 병합이나 역할 부여는 실행하지 않습니다.

실제 테스트는 전용 참가자 앱·테스트 계정으로 동의/거절, 만료 state·다른 브라우저·로그아웃 후 콜백, 회원 탈퇴·권한 변경 중 콜백, 로컬 해제·재연결, 서버 A/B 격리, 앱/키 변경 후 재연결, 백업 복원 뒤 과거 기록 처리를 확인합니다. 현재 이 실제 계정 검증은 **PENDING**입니다. 코드와 검증 범위는 [v5.2.7 보고서](workspace-review-v527.md)에 기록합니다.

## 실제 계정 E2E — 아직 PENDING

로컬 가상 API 테스트 통과는 실제 OAuth·Discord 권한·카페 쓰기 권한을 증명하지 않습니다. 공개 활성화 전에 다음 표를 실제 검증 기록으로 채웁니다.

| 순서 | 확인 내용 | 기대 결과 |
|---|---|---|
| 1 | 제작자 로그인, 운영자/참가자의 제작자 API 접근 | 제작자만 허용, 나머지는 403 |
| 2 | 서버 A·B 운영자가 서로의 URL에 접근 | 현재 회원/서버 관리 권한에 따라 차단 |
| 3 | A·B의 서로 다른 CHZZK 방송 소유자 연결 | 인증 대상이 각 서버에만 반영 |
| 4 | 참가자 별도 계정의 팔로우/미팔로우 인증 | 성공 시 해당 서버의 인증 역할만 부여, 미팔로우는 거절 |
| 5 | Discord 참가 → 카페 접수 → 통합 Queue | 각 서버의 순서에만 반영, 중복 정책 유지 |
| 6 | 호출 → 응답 → 노쇼 → 다음판/다다음판 | 본인 작업만 가능, 호출 상태 일관성 유지 |
| 7 | 준비 확인 → 추첨 → 팀 배정 → OBS | 해당 서버 참가자·결과만 표시 |
| 8 | 타 서버 OBS 토큰으로 접근 | 403, 올바른 서버 토큰은 허용 |
| 9 | 운영자 권한 제거/서버 탈퇴 후 조작 | 다음 쓰기 요청에서 차단, 읽기 캐시 최대 15초 |
| 10 | 긴급 잠금 → 서버 재시작 → 잠금 해제 | 외부 전송 중단, Queue·연결 파일 복구 |
| 11 | 방송 종료·기록 확인 → 전체 볼륨 백업 복원 | 두 서버 데이터·원래 키로 복구 |

현재 별도 참가자 계정이 없어 실제 팔로워 역할 부여 검증은 PENDING입니다. 검증을 위해 다른 사람의 인증정보를 수집하지 않습니다.

기존 제작자 대시보드의 고급 OBS 편집·Runbook·Preflight 등은 그대로 보존했습니다. 새 포털은 일상 방송 운영 중심입니다. 기존 고급 화면 전체를 일반 사용자에게 공개하는 것은 이번 배포의 범위가 아니며, 제작자 진단 API는 계속 차단합니다.

## v5.2.1 운영 시작 안내·인수인계

운영자는 통합 운영 → 운영 준비에서 한 기능씩 확인합니다. 운영 시작 안내는 현재 서버에 저장된 연결·채널·역할·게시판·OBS 설정과 다음 설정 화면을 보여 줍니다. 새로고침은 안내 조회만 실행하며 실제 글 게시나 역할 부여를 실행하지 않습니다. 현재 Discord 접근 권한은 기존 인증 경로에서 확인합니다.

설정 완료 표시는 실서비스 검증 성공이 아닙니다. 실제 OAuth·카페 쓰기·팔로워 역할 부여·서버 재시작은 위 E2E 절차로 검증합니다. 네이버는 카페를 사용하지 않는 경우 선택 항목이며, 만료된 저장 토큰은 현재 사용 가능한 토큰으로 표시하지 않습니다.

운영 인수인계는 개인정보와 토큰·OBS 전용 주소를 제외한 텍스트 요약을 복사·저장합니다. 전체 운영 데이터 복구에는 이 요약이 아니라 원래 암호화 키와 /app/data 전체 백업이 필요합니다. 제작자 진단과 복구 기능은 계속 제작자 화면에서 관리합니다.

## v5.2.2 참가 설정·운영 연습

통합 운영 → 참가 설정에는 **참가 선발 규칙**과 **호출 응답 시간**을 따로 제공합니다. 공정 선발 규칙은 다음 모집부터 적용하며 저장 시 기존 알림 채널·구독 역할과 진행 중인 회차의 정책을 보존합니다. 오늘 미참가 우선은 기존 KST 기준이고 신규 참가자 판단은 저장된 최근 회차 기록 범위를 사용합니다.

호출 응답 시간은 15~300초 사이 정수입니다. 현재 호출의 마감은 바꾸지 않고 다음 호출부터 적용합니다. 서버별 설정을 저장하므로 새 서버마다 Railway 환경변수를 추가할 필요는 없습니다. 다른 창에서 먼저 바꾸면 저장 충돌을 표시하며 새 설정을 불러온 후 검토·저장합니다.

호출 설정은 해당 operationsFile + `.call-settings.json`에 보관합니다. 전체 `/app/data` 백업에 포함하지만 기존 Queue/회차 복원 지점에는 포함하지 않습니다. 코드 롤백은 파일을 삭제하지 않으며 이전 코드의 호출 시간 기준을 다시 사용하므로 되돌릴 때 확인합니다.

공개 포털 활성화 시 재시작 후 저장된 호출 시간을 복원합니다. `MULTI_WORKSPACE_ENABLED=false`인 기존 단일 서버 모드는 매 재시작마다 `PARTICIPATION_CALL_TIMEOUT_SECONDS`를 우선하고 호출 설정 파일을 읽거나 새로 만들지 않습니다. 포털 비활성화는 기존 파일을 삭제하지 않으므로 다시 활성화하면 저장했던 값을 사용합니다.

통합 운영 → 운영 준비 → **운영 연습**에서 가상 접수 → 호출 → 준비 → 추첨 → 팀 배정 → 종료를 한 단계씩 진행합니다. 실제 API나 참가자 데이터를 사용하지 않고 페이지·서버 변경 시 초기화합니다. 연습 통과를 실서비스 연결이나 서버 재시작 검증 성공으로 표시하지 않습니다.

## v5.2.3 참가 접수 조건

통합 운영 → 참가 설정에서 아래 세 소분류를 한 화면씩 사용합니다. 기존 참가 선발 규칙·호출 응답 시간도 별도 화면으로 유지합니다.

| 화면 | 입력 | 적용과 제한 |
|---|---|---|
| 접수 인원 제한 | 0~1000명 사이 정수 | 0은 무제한. 정원은 추첨할 모집 인원 이상이어야 합니다. |
| 중복 접수 처리 | 기존 순번 유지 / 중복 거절 | 유지 시 기존 접수 항목과 순서를 사용하며 새 항목을 만들지 않습니다. |
| 정원 도달 마감 | 사용 / 사용 안 함 | 사용하려면 정원이 1명 이상이어야 합니다. |

서버를 선택하고 해당 화면의 값을 저장합니다. 저장은 다른 두 접수 조건도 함께 보존하며 **다음 모집부터** 적용합니다. 이미 열려 있는 Discord 모집과 네이버 접수의 정책·참가 순서·예약은 변경하지 않습니다. 네이버 게시 요청이 대기 중일 때 설정을 바꿔도 게시 시작 시 고정한 정책을 사용합니다. 다른 운영자가 먼저 저장하면 409 충돌을 표시하며 입력을 보존합니다. 최신 설정을 불러와 검토한 뒤 다시 저장합니다.

세 조건은 서버별 operations 파일에 원자적으로 저장합니다. 조회와 저장은 현재 서버 운영자 권한을 확인하고 참가자에게 허용하지 않습니다. 저장은 CSRF·Origin과 전역/서버 운영 잠금을 검사하며 실제 저장 큐 실행 시점에도 잠금을 재확인합니다. 설정 저장만으로 Discord 메시지·역할을 바꾸거나 카페 글을 게시하지 않습니다.

정원은 **Discord 모집과 네이버 접수에 각각 적용**합니다. Discord 30명과 네이버 30명을 설정하면 둘의 합계가 30명으로 제한되는 방식이 아닙니다. 운영자의 별도 수동 Queue 등록은 이 조건을 사용하지 않습니다. Discord는 Discord 사용자 ID, 네이버는 기존 접수 이름 기준으로 중복을 판단합니다. 두 서비스의 계정이 같은 사람임을 검증하는 매핑이 없으므로 같은 닉네임만으로 계정을 합치지 않습니다. 이 범위는 통합 Queue의 기존 표시·호출 기능을 삭제하거나 변경하지 않습니다.

조건을 아직 한 번도 저장하지 않은 서버에서는 Discord의 기존 중복 순번 유지와 네이버의 기존 중복 거절을 각각 유지합니다. 처음 저장하면 저장한 중복 정책을 다음 Discord 모집과 다음 네이버 게시에 적용합니다. 어느 한 화면에서 첫 저장을 할 때도 현재 세 조건을 함께 확인합니다.

미루기와 다음 회차 예약은 기존 약속을 보존합니다. 정원을 줄인 뒤 열리는 회차에 이월 참가자가 정원 이상이어도 삭제하지 않으며 새 접수를 막습니다. 이후 회차로 미룬 참가자는 현재 활성 정원 계산에서 제외하고 현재 회차로 다시 신청할 때는 정원을 확인합니다. 접수 정원과 추첨할 인원은 다른 값이며, 모집 열기·모집 인원 변경 모두 추첨 인원이 정원을 넘으면 거절합니다.

정원 자동 마감 후에는 기존 마감 상태의 신청·취소·미루기 제한을 따릅니다. Discord는 추첨 전 **모집 다시 열기**로 현재 회차를 열 수 있고 현재 회차 정책을 유지합니다. 꽉 찬 상태에서는 새 접수를 계속 막으므로 참가 취소·미루기로 자리를 비운 뒤 접수합니다. 같은 사람의 순번 유지 요청만으로 다시 자동 마감하지 않습니다. 네이버는 기존 흐름대로 초기화 후 새 모집을 열며 자동 재개하지 않습니다. 기존 시간 기반 자동 마감도 유지합니다.

새 접수 기본 설정과 Discord 회차 정책은 기존 operations의 일부이므로 기존 Queue/회차 복원 지점에 함께 포함됩니다. 네이버 접수·게시·보관 기록의 정책은 네이버 접수 저장소와 그 정상 백업 및 전체 볼륨 백업으로 보존합니다. Queue 복원 지점이 네이버 접수 전체까지 복원하는 것으로 해석하지 않습니다.

필드가 없는 구형 데이터는 호환 기본값을 사용합니다. 정책 필드가 있는데 null·잘못된 범위·알 수 없는 항목인 데이터는 기본값으로 바꾸지 않고 거절합니다. 정상 `.bak` 등 복구 후보가 있으면 기존 JsonStore 복구 경로로 복원하며 모든 후보가 손상된 경우 원본을 덮어쓰지 않습니다. 복원 지점도 digest뿐 아니라 정책을 검증합니다. 코드 롤백은 파일을 삭제하지 않지만 이전 코드가 새 정원·중복 정책을 집행하지 않으므로 롤백 후 모집 조건을 확인해야 합니다. 전체 `/app/data`와 기존 암호화 키 보존은 계속 필요합니다.

새 필수 환경변수, Discord 권한, Gateway Intent는 없습니다. 실제 OAuth·역할 부여·카페 게시·운영 재시작 E2E는 여전히 PENDING입니다. 가상 화면 테스트를 실제 서비스 연결 성공으로 표시하지 않습니다.


## v5.2.4 참가자 접수 안내

사용자 홈 → 내 참가 화면에서 현재 Discord 모집의 정원, 활성 접수 인원, 남은 자리와 마감 사유를 확인합니다. 네이버 접수·운영자 수동 Queue를 합산하지 않으며, 추첨 선발 인원은 접수 정원과 별개입니다. 다음 모집용 설정을 저장해도 현재 안내는 현재 회차 정책을 유지합니다.

정원이 없으면 무제한, 다음판·다다음판으로 미룬 접수는 활성 인원에서 제외합니다. 현재 회차로 이월된 예약은 포함하되 정원보다 많아도 삭제하지 않고 남은 자리를 0으로 표시합니다. 정원 도달 상태의 신규 신청은 차단하지만 열려 있는 회차의 기존 참가자 취소·미루기는 유지합니다. 마감된 모집은 자리가 비어도 운영자가 다시 열기 전에는 신규 접수를 받지 않습니다.

접수 시간 만료, 운영자 마감, 정원 자동 마감과 추첨 이후 진행을 구분합니다. 이전 버전에서 시간 마감이 이미 manual로 저장됐다면 과거 원인을 추정해 변경하지 않습니다. 새 마감부터 실제 마감 시각을 기준으로 기록합니다.

조회 실패·권한 상실·오래된 모집 링크는 이전 정원과 참가 버튼을 계속 보여주지 않습니다. 현재 회차 안내는 준비 확인 API 실패와 독립적으로 갱신하며 늦게 도착한 이전 요청이 최신 응답을 덮지 않게 합니다. API의 최종 참가 검사는 계속 유지하므로 화면에 자리가 있어도 동시 신청으로 정원이 먼저 차면 거절될 수 있습니다.

집계는 로컬 상태로 만들고 다른 참가자의 이름·ID를 추가하지 않습니다. 서버별 접수 조회는 Discord 멤버십을 fresh read로 확인하며 동시 확인 요청은 기존 in-flight 경로를 공유합니다. 신규 커넥터 쓰기·토큰 갱신·역할 부여는 없습니다. 새 환경변수·Gateway Intent·권한·저장 파일·스키마 변경은 없습니다.

v5.2.4에서는 현재 모집 마감 후 패스 예약 변경을 409로 차단했습니다. 이 제한은 아래 v5.2.5의 호출 전용 예약 복구 경로로 개선합니다. 일반 모집 버튼과 추첨 이후 예약 변경 제한은 유지합니다.

## v5.2.5 마감 후 호출 패스·예약 복구

현재 Discord 모집에서 호출을 받은 본인은 **내 참가 화면**이나 Discord 호출 메시지의 **이번판 패스**를 누를 수 있습니다. 실제 호출 응답 기한 안이고 아직 추첨 전이면, 접수 중이거나 수동·정원·시간으로 마감됐어도 다음판으로 예약합니다. 접수 마감 시간과 호출 응답 기한은 서로 다릅니다. 일반 참가·취소·다음판/다다음판 미루기 버튼은 기존 접수 중 제한을 유지합니다.

| 현재 모집 상태 | 현재 회차의 호출 패스 |
|---|---|
| 접수 중, 접수 시간이 지난 open | 정확한 본인 호출의 응답 시간 안이면 허용 |
| 수동·정원·시간 마감 closed | 같은 조건으로 허용 |
| 추첨 완료 drawn, 참석 확인 checking | 예약 변경은 거절하고 진행자에게 요청 |
| 종료 ended | 예약 변경 거절 |

호출의 참가 응답은 기존 경로를 유지하며 호출 시간 만료·사용자 불일치·잘못된 토큰은 계속 거절합니다. 수동 Queue나 현재 모집과 무관한 호출 패스는 기존 Queue 전용 동작이며 새 회차 예약을 임의로 만들지 않습니다. 패스 때문에 추첨 가능한 인원이 부족해지면 기존 인원 검증에서 차단되므로 운영자가 모집 인원을 확인합니다. 당첨자·참석 확인·팀 결과를 자동으로 지우거나 재추첨하지 않습니다.

예약 결정과 미루기 표시는 Operations에 함께 저장하고 Queue에 반영합니다. Queue 저장이 지연되면 **패스 반영 확인 중**으로 표시하며 확인 중인 호출의 새 응답·예약 변경을 막습니다. 이미 저장한 결정을 재시도·재시작에서 이어 반영하므로 같은 예약을 두 번 만들거나 취소한 예약을 되살리지 않습니다. 두 파일을 동시에 하나의 원자적 트랜잭션으로 저장하는 구조는 아닙니다.

같은 패스의 자동 호출은 정해진 다음 대상만 재사용합니다. 수동 호출이 진행을 인계받으면 오래된 패스 재시도로 그다음 사람까지 호출하지 않습니다. 원래 모집이 종료·변경되면 이전 패스의 자동 진행도 중단합니다. 자동 호출 전송이 실패하더라도 저장된 예약은 유지하고 진행자에게 확인을 안내합니다. Discord 메시지를 보내기 전 잠금·종료·모집 변경을 재확인합니다.

참가자 화면의 고정 호출 버튼도 새 상태를 반영합니다. 참가자 API에는 본인 결과와 공개용 오류 안내만 반환하며 다음 참가자의 이름·ID·호출 토큰과 내부 결정·진행 기록을 넣지 않습니다. 전체 서버 Queue 조회는 기존 운영자 권한을 따릅니다. 새 API 엔드포인트·필수 환경변수·Gateway Intent·권한·저장 파일은 없으며 기존 두 파일에 호환 필드를 추가합니다. 데이터 스키마는 2입니다.

### 복원과 이전 코드 롤백

Operations만 복원하면 미완료 패스 결정과 현재 Queue가 다를 수 있습니다. 해당 호출의 증거가 없거나 새 호출로 바뀌었다면 자동 예약 추측 대신 운영을 중단합니다. 제작자가 원본을 보존하고 서로 일치하는 `/app/data` 전체 백업·기존 암호화 키로 복구해야 합니다. 내부 기록을 지우거나 토큰을 복사해 해결하지 않습니다.

이전 코드에는 이 결정 복구 절차가 없으므로 **코드 롤백 전 요청·타이머를 중지하고 미완료 패스 결정과 자동 진행이 없는지 검토**합니다. 대기 중이라면 v5.2.5에서 정상 저장·복구를 마친 뒤 전체 데이터를 백업하거나, 제작자가 일치하는 전체 데이터 복원을 계획해야 합니다. 이는 운영 절차이며 Release Center에 새 자동 차단 게이트를 추가한 것은 아닙니다. 코드 롤백은 이미 보낸 Discord 메시지나 운영 데이터를 되돌리지 않습니다. 기존 Update JSON의 서명 필수 정책도 그대로 유지합니다.

실제 Discord·네이버·CHZZK 인증과 참가자 E2E, Railway의 새 버전 배포는 계속 PENDING입니다. 로컬 가상 API·화면·저장 실패 시험을 실제 서비스 인증 성공으로 표시하지 않습니다.

## v5.2.6 내 호출 응답 기록·상태 재확인

참가자는 **내 참가 화면**에서 자기 호출의 상태를 확인합니다. 현재 모집·게임·회차와 본인 Queue 항목·호출 시도가 모두 일치하는 패스 결정 기록만 표시합니다. 다른 호출에서 같은 참가자를 다시 불렀다면 이전 기록을 새 호출의 응답으로 표시하지 않습니다.

| 화면 상태 | 의미 | 다음 행동 |
|---|---|---|
| 지금 호출 | 현재 호출의 응답 시간이 남음 | 참가 가능 또는 이번판 패스로 응답 |
| 패스 확인 중 | 패스 결정은 저장됐지만 Queue 반영 확인이 끝나지 않음 | 상태 다시 확인으로 조회하고 중복 응답하지 않음 |
| 패스 응답 기록됨 | 해당 호출 당시 Queue 저장까지 확인한 과거 기록 | 현재 예약은 아래 예약 목록에서 따로 확인 |
| 현재 Queue 상태: 참가 확인 | 현재 Queue가 joined임 | 진행자 안내 확인; 별도 영속 참가 결정의 증명은 아님 |
| 처리 결과 불확실 | 호출 응답 전송 뒤 연결 중단 등으로 결과를 확인하지 못함 | 상태 다시 확인을 누르고 필요하면 진행자에게 문의 |
| 응답 시간 지남 | 현재 호출의 응답 기한이 지남 | 새 응답 없이 조회하거나 진행자에게 문의 |

패스 응답 기록은 **현재 예약 유지나 Discord 메시지 전달 성공을 뜻하지 않습니다.** 나중에 예약이 취소되거나 다음 회차로 소비돼도 과거 응답이 수락된 사실과 현재 예약 목록은 서로 다를 수 있습니다. 현재 모집이나 호출 시도가 바뀌면 이전 기록을 보여주지 않습니다. 완료 기록은 기존 최근 200건 보관 정책을 따르며, 정리된 기록·구형 데이터의 필드 부재는 알 수 없음입니다. 이를 실패로 표시하거나 기록 복구를 위해 예약을 재생성하지 않습니다.

상태 다시 확인은 기존 참가 상태 GET만 사용합니다. 호출 응답 POST를 자동으로 다시 보내거나 새 주기 조회를 추가하지 않습니다. 새 Viewer는 화면의 entryId·attempt·sessionId를 함께 보내며 서버는 현재 호출과 다르면 거절합니다. 이 선택 필드를 보내지 않는 기존 HTTP 클라이언트는 기존 검증과 호환합니다. 호출의 비밀 토큰이나 내부 결정 digest를 조회 결과에 새로 포함하지 않습니다.

Discord **내 시참**에서 새로 표시되는 참가 가능·이번 호출 패스 버튼도 해당 호출 시도에 결합됩니다. 예전 내 시참 호출 버튼은 최신 내 시참을 다시 열도록 안내하므로 이전 버튼으로 새 재호출에 응답할 수 없습니다. 일반 호출 메시지의 기존 queuecall 토큰 버튼은 그대로 사용합니다. 호출 digest는 권한 증명이 아니며 본인 Discord 인증·서버 경계·Queue 비밀 토큰의 기존 검증을 유지합니다.

조회에서는 Operations·Queue를 저장하거나 미완료 결정을 확인 처리하지 않습니다. 기록 손상·같은 호출 문맥의 충돌은 일반 503 안내로 차단하고 내부 정보는 공개하지 않습니다. 제작자는 기존 복구 절차로 원본을 보존해 점검합니다. 새 필수 환경변수·Discord 권한·Gateway Intent·영구 데이터 파일·스키마 변경은 없으며 위 v5.2.5의 전체 볼륨 백업 및 미완료 결정 롤백 제한을 그대로 따릅니다. 실제 계정 OAuth·팔로워 역할 부여·운영 E2E와 Railway 새 버전 배포는 계속 PENDING입니다.
