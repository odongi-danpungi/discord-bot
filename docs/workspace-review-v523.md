# v5.2.3 참가 접수 조건 검토

검토일: 2026-10-12 (Asia/Seoul). 직전 개발 기준은 v5.2.2 / 5e73c5d474f73190fb810363606d04cb0c7e5cf3입니다. main 기준은 v5.1.7 / 7898f1d98b2df3164a2427503ff373a213af4403이며 Railway 운영도 v5.1.7입니다. 기존 PR #11의 배포 후보를 계속 개발합니다. 이번 변경은 Discord·네이버 카페·CHZZK, 통합 Queue, 기존 운영·점검·복구 기능을 유지하고 데이터 스키마 2와 기본 비활성 포털을 보존합니다.

## 구현과 적용 시점

통합 운영 → 참가 설정에 **접수 인원 제한**, **중복 접수 처리**, **정원 도달 마감**을 개별 화면으로 추가했습니다. 화면에는 해당 기능의 입력과 적용 시점을 표시합니다. 기존 참가 선발 규칙과 호출 시간 화면도 유지합니다.

| 항목 | 허용값 | 동작 |
|---|---|---|
| maxApplicants | 0~1000명 사이 정수 | 0은 무제한이며 활성 접수 참가자만 계산합니다. |
| duplicatePolicy | keep_existing / reject | 기존 접수 순번 유지 또는 중복 요청 거절입니다. |
| closeOnCapacity | boolean | 정원에 도달하면 기존 마감 상태로 전환합니다. true에는 1명 이상 정원이 필요합니다. |

운영자 전용 GET/POST `/w/:guildId/intake-settings`를 제공합니다. POST는 위 세 값과 revision 네 항목만 받으며 자료형·범위·필드 수를 검증합니다. 저장 시 settings revision과 operations revision을 함께 올립니다. 오래된 화면은 409로 거절하고 다른 두 접수 조건을 보존합니다. 현재 모집·Queue·예약은 건드리지 않습니다.

Discord 모집을 열 때 서버의 저장 조건을 회차 정책으로 고정합니다. 네이버 카페 게시 요청을 시작할 때도 정책을 먼저 저장하므로 외부 응답 대기 중 설정을 바꿔도 해당 게시·모집에 새 정책이 섞이지 않습니다. 설정 변경은 다음 모집부터 적용합니다. 기존 시간 기반 마감과 수동 마감은 유지합니다.

접수 정원은 추첨할 모집 인원과 다릅니다. 제한 정원이 있으면 모집 열기와 인원 변경 모두 추첨 인원이 정원을 초과하지 않게 합니다. 다음 회차로 약속한 이월 참가자는 정원이 줄어도 보존하고 추가 접수를 거절합니다. 이후 회차로 미룬 참가자는 현재 활성 정원에서 제외하며 현재 회차로 다시 신청할 때 정원을 확인합니다.

정원 자동 마감 후의 신청·취소·미루기는 기존 마감 규칙을 따릅니다. Discord 다시 열기는 현재 회차 정책을 유지하고 꽉 찬 상태의 신규 접수는 계속 막습니다. 기존 순번 유지 요청은 중복 항목을 추가하지 않으며 다시 열었던 회차를 자동으로 마감시키지 않습니다. 네이버는 기존 초기화 후 새 모집 흐름을 유지하며 자동 재개하지 않습니다.

## 호환 범위와 한계

Discord 모집과 네이버 접수는 **각각 정원을 계산**합니다. 합산한 통합 Queue의 인원을 제한하는 기능은 아닙니다. 운영자의 별도 수동 Queue 등록은 기존 동작을 유지합니다. Discord 사용자 ID와 네이버 접수 이름을 같은 사람으로 검증하는 계정 매핑이 없으므로 닉네임만으로 두 서비스의 참가자를 합치지 않습니다. 기존 통합 Queue·호출·팀 배정 기능은 유지합니다.

설정을 아직 저장하지 않은 서버에서 Discord는 기존 중복 순번 유지, 네이버는 기존 중복 거절을 사용합니다. 처음 저장한 이후의 모집부터 저장된 정책을 적용합니다. 구형 데이터에 새 필드가 없으면 호환 기본값을 사용하되 필드가 존재하면서 손상된 경우에는 기본값으로 덮지 않습니다.

CHZZK 연결·팔로워 인증에는 이번 버전의 새로운 API 요청이나 권한을 추가하지 않습니다. 운영 연습과 기존 준비 안내도 유지합니다. 이번 검토는 접수 설정 및 연관 저장·복원·참가자 경로에 대한 검토이며 모든 기존 모듈의 실제 외부 서비스 E2E를 새로 완료한 것으로 표현하지 않습니다.

## 권한·보안·저장·복구

조회와 저장은 현재 Discord 서버의 운영자 권한을 재확인합니다. 참가자와 타 서버 운영자의 접근, 만료된 권한을 거절합니다. 저장은 기존 CSRF·Origin·전역/서버 긴급 잠금·draining 검사를 사용하고 저장 큐 안에서도 운영 guard를 확인합니다. 설정 저장은 외부 글 게시·Discord 메시지나 역할 변경을 실행하지 않습니다.

UI는 하나의 기능만 편집하고 다른 두 값을 보존합니다. 잘못된 정수·정원 없는 자동 마감·설정 응답 누락을 차단하고, 저장 충돌이면 현재 입력을 남겨 운영자가 다시 불러올 수 있게 합니다. 서버·페이지 전환 뒤의 늦은 응답과 오래된 폼 저장을 차단합니다. 텍스트 기반 렌더링과 기존 입력 보호를 유지합니다. 실제 토큰·비밀번호·참가자 개인정보를 새 설정에 저장하지 않습니다.

기본 조건은 기존 operations 파일의 intakeSettings에, 현재 회차 정책은 session.intakePolicy에 저장합니다. 원자 저장과 revision 충돌 검사로 서버별 변경을 직렬화합니다. OperationsStore의 로드·변경 전후 검증과 복원 지점 검증은 같은 정책 검사를 사용합니다. digest가 재계산된 백업도 정책이 잘못되면 거절합니다. 유효한 구형 필드 누락은 계속 허용합니다.

네이버 저장소는 게시 대기·현재 모집·보관 기록의 선택적 정책을 검사합니다. 정상 기본 파일·백업을 우선하는 기존 복구 경로를 유지하며 모든 후보가 손상되면 EDATA_CORRUPT로 중단하고 파일 바이트를 보존합니다. 새 설정과 Discord 회차 정책은 기존 Queue/회차 복원 지점에 포함됩니다. 네이버 접수 전체 복구에는 네이버 저장소 백업 또는 전체 `/app/data` 볼륨이 필요합니다.

코드 롤백은 저장된 설정을 삭제하지 않지만 이전 코드가 새 접수 정책을 집행하지 않으므로 롤백 후 모집 조건을 확인해야 합니다. 기존 호출 설정은 별도 파일이며 여전히 Queue/회차 복원 지점의 범위 밖입니다. 기존 NAVER_TOKEN_KEY·CHZZK_TOKEN_KEY, 전체 볼륨과 단일 replica를 유지합니다. 새 필수 환경변수·Discord 권한·Gateway Intent와 데이터 스키마 변경은 없습니다.

## 수정한 오류와 변경 파일

- 모집 중 추첨 인원을 접수 정원보다 크게 변경할 수 있던 경로를 차단했습니다. 새 모집과 resize 모두 현재 정책을 확인하고 거절 시 기존 상태를 보존합니다.
- 접수 조건이 잘못된 operations 기본 파일·백업·복원 지점을 유효한 상태로 받아들이면 후속 저장이 막힐 수 있었습니다. 저장 경계와 복원 경계에서 정책을 검증하고 정상 후보 복구·구형 데이터 호환을 회귀로 확인합니다.
- 네이버 게시·모집·보관 기록에 명시적인 손상 정책이 있어도 로드가 허용되던 경로를 차단했습니다. 필드 없음과 null·잘못된 필드의 의미를 구분합니다.
- 참가자 API가 error.status를 무시해 접수 정원 409를 400으로 응답하던 문제를 수정했습니다. 명시적 409·503을 보존하며 ENOSPC 등 저장소 오류와 TypeError 등 내부 오류는 500으로 분류하고 상세 오류·경로를 숨깁니다.
- JsonStore에서 변경 callback의 정상적인 중복·revision·입력 거절까지 저장 실패로 기록해 후속 flush가 실패하던 문제를 수정했습니다. 거절은 호출자에게 그대로 반환하고 저장되지 않은 변경도 반영하지 않습니다. 실제 파일 I/O 실패는 flush에서도 계속 전파하며 정상 후속 저장이 완료될 때 해제합니다. 초기 로드·읽기 실패도 숨기지 않습니다.

추가 파일은 `src/intake-policy.js`, `test/intake-policy.test.js`, `docs/workspace-review-v523.md`입니다. 삭제 파일은 없습니다.
