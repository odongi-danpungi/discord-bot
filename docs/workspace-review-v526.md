# v5.2.6 내 호출 응답 기록·안전한 상태 재확인 검토

검토일: 2026-10-15 (Asia/Seoul). 직전 개발 기준은 v5.2.5 / 87152b06850dc4534459c4e82304f31f86a17bc1입니다. main과 실제 Railway 기준은 v5.1.7 / 7898f1d98b2df3164a2427503ff373a213af4403입니다. 기존 초안 PR #11에서 개발하며 Discord·네이버 카페·CHZZK, 통합 Queue·예약·호출·추첨·팀 배정·OBS·방송 운영과 제작자 점검·복구 기능을 보존합니다. 이번 검토 범위는 참가자의 본인 호출 결과 조회, 표시와 오래된 호출 버튼의 경계입니다. 기존 모든 코드의 새로운 전수 감사를 의미하지 않습니다.

## 사용자 동작과 표시의 의미

내 참가 화면은 현재 호출, 패스 확인 중, 패스 응답 기록, 현재 Queue의 참가 확인, 응답 만료와 연결 중단 뒤 결과 불확실을 구분합니다. 패스를 수락한 뒤 Queue 반영 확인이 끝나지 않았다면 확인 중으로 표시하고 중복 응답을 막습니다. 확인 저장까지 끝났으면 당시 패스 응답 기록을 표시합니다.

확인된 과거 기록은 현재 예약 유지나 Discord 전송 완료를 보장하지 않습니다. 예약 취소·다음 회차 소비와 과거 수락 사실은 구분하며 현재 예약은 기존 예약 목록에서 확인합니다. 참가 가능 응답에는 패스와 같은 영속 결정 기록이 없으므로 현재 Queue의 참가 확인 상태만 중립적으로 표시합니다. 영속 참가 응답 증명이나 메시지 전달 확인 기능을 추가했다고 주장하지 않습니다.

호출 응답을 보낸 뒤 네트워크 연결이 끊기거나 응답을 해석하지 못하면 처리 결과가 불확실하다고 안내합니다. 참가자는 상태 다시 확인으로 기존 참가 상태를 조회합니다. 자동 POST 재전송이나 새 폴링을 추가하지 않습니다. 조회가 확인 근거를 제공하지 못하면 성공·실패를 임의로 추정하지 않고 현재 상태와 진행자 확인을 안내합니다.

## 본인·호출 문맥에 한정한 읽기

새 `buildParticipantCallResponse`는 기존 Operations 결정 기록을 읽기만 합니다. 현재 Operations의 session id·game·round, 본인 Discord Queue 항목 id·discordUserId·sessionId·game·round·callAttempt가 결정 기록과 정확히 일치해야 합니다. 같은 Queue ID가 새 회차에 재사용되거나 참가자가 다시 호출됐다고 이전 패스 기록을 새 호출 결과로 이어 붙이지 않습니다.

반환하는 `queue.callResponse`는 null 또는 아래 최소 필드입니다.

```text
{ action:'pass', state:'confirming'|'recorded', sessionId, game,
  round, targetRound, attempt, recordedAt, confirmedAt }
```

`appliedAt=null`이면 confirming, 확인 시각이 있으면 recorded입니다. recorded는 과거 Queue 기본 파일 저장의 확인이며 이후 Queue 상태·예약 취소·응답 기한이 바뀌었다고 수락 사실을 재작성하지 않습니다. 확인 중에는 Queue가 이미 적용돼 있어도 확인 저장이 끝났다고 추정하지 않습니다. 다른 사용자·소스·호출 시도·모집 문맥은 요약 대상이 아닙니다.

필드 없는 구형 데이터, 현재 문맥 부재와 보관 범위를 벗어나 정리된 기록은 null이며 실패가 아닙니다. 완료된 기록 최근 200건과 미완료 최대 1,000건의 기존 보관 정책을 변경하지 않습니다. 기록 손상과 같은 호출 문맥의 중복 충돌은 `participant_call_result_unavailable`과 고정된 일반 안내의 503으로 차단합니다. 내부 오류·토큰·다른 참가자 정보는 응답에 넣지 않습니다.

이 읽기 함수는 Operations·Queue 저장, receipt 확인 저장, 예약 재생성, Queue 복구 투영이나 외부 API 쓰기를 하지 않습니다. 기존 상태 API의 인증·현재 서버 멤버십·서버 격리 경로를 유지합니다. 새로운 상태 요약을 인증 토큰이나 운영 승인 자료로 사용하지 않습니다.

## 화면과 Discord 버튼의 호출 결합

새 Viewer의 호출 요청은 선택 필드 `expectedCall={entryId,attempt,sessionId}`를 포함합니다. 서버는 필드 형식과 현재 호출의 일치를 확인하며, 오래 열린 화면의 버튼이 새 재호출에 응답하는 것을 거절합니다. 잘못된 형식은 400, 다른 현재 호출은 409로 구분합니다. 이 필드를 보내지 않는 기존 HTTP 클라이언트는 기존 본인·호출·비밀 토큰 검증 경로와 호환합니다. 새 Viewer는 비밀 Queue 토큰을 내려받거나 브라우저에 추가 보관하지 않습니다.

Discord 내 시참의 새 호출 버튼은 현재 모집과 Queue 항목·시도·항목의 모집 문맥을 묶은 SHA-256 digest를 사용합니다. custom ID는 100자 미만이며 길이가 긴 모집·항목 ID를 그대로 이어 붙이지 않습니다. 이 digest는 표시된 호출을 식별하는 값이며 권한 증명이 아닙니다. Discord 사용자, 현재 서버와 Queue의 비밀 호출 토큰에 의한 기존 검증을 유지합니다.

이전 비결합 `community:act:call_join`·`call_pass` 버튼은 최신 내 시참을 다시 열도록 안내합니다. 오래된 버튼을 현재 호출에 임의로 연결하지 않습니다. 일반 호출 메시지의 기존 `queuecall:` 토큰 버튼은 변경하지 않습니다. 참가·패스 외 일반 모집 버튼의 기존 회차 검증과 인증 보호도 유지합니다.

## 보안·저장·호환성

본인 응답 요약에는 다른 참가자의 이름·ID, 원본 호출 토큰·내부 receipt ID·자동 진행 대상·원시 저장 오류를 추가하지 않습니다. 화면은 허용된 고정 문구와 본인 상태를 사용합니다. 공개 조회가 복구 증거를 수정하거나 기존 저장 오류를 지우지 않습니다. 기록 확인 실패가 성공 색상이나 성공 안내로 남지 않도록 처리합니다.

새 필수 환경변수·Discord 권한·Gateway Intent·영구 데이터 파일·데이터 스키마 변경은 없습니다. 스키마 2, 기본 비활성 포털, JSON 파일을 사용하는 replica 1 단일 프로세스 운영을 유지합니다. 별도 처리량·지연 벤치마크를 수행하지 않았으므로 성능 수치 개선을 주장하지 않습니다.

v5.2.5의 Queue → Operations 잠금 순서, 패스 결정 저장·Queue 적용·확인 복구, 호출별 자동 진행과 운영 잠금·종료 경계를 보존합니다. [직전 검토 보고서](workspace-review-v525.md)의 지원 단계·추첨 후 제한·복구 절차가 계속 적용됩니다. 새 조회 화면이 다중 파일 원자적 트랜잭션이나 외부 Discord exactly-once 전송을 제공하는 것은 아닙니다.

## 백업·복원·롤백

기존 복원 지점에는 Operations의 예약·결정 기록이 있지만 Queue 파일 전체가 포함되지는 않습니다. 미완료 결정과 Queue 증거가 다르면 fail-closed로 점검해야 합니다. 상태 요약이 null이라고 내부 기록을 삭제하거나 예약을 재생성하지 않습니다. 서로 일치하는 `/app/data` 전체와 원래 NAVER_TOKEN_KEY·CHZZK_TOKEN_KEY를 함께 보존합니다.

이전 코드로 롤백하기 전 요청·타이머를 중지하고 미완료 패스 결정과 자동 진행을 검토합니다. 필요하면 v5.2.5 이상에서 정상 저장·복구를 마친 뒤 전체 볼륨을 백업하거나 제작자가 일치하는 전체 데이터 복원을 계획합니다. 이 절차를 강제하는 새 자동 Release Center 게이트는 추가하지 않았습니다. 코드 롤백은 운영 데이터와 이미 보낸 외부 메시지를 자동으로 되돌리지 않습니다.

## 실제 서비스 상태와 배포 전 작업

실제 참가자 계정 E2E는 PENDING입니다. 사용자는 별도 참가자 테스트 계정이 없다고 답했으며, 실제 서비스 인증 성공을 가정하지 않습니다. Discord 로그인 → 참가 → 호출 → 마감 후 패스 → 결과 조회 → 예약 취소·재호출 → 재시작 복구와 별도 CHZZK 팔로워 역할 부여를 실제 계정으로 확인해야 합니다. 운영자 A/B의 서버·방송 분리, 네이버 접수, 준비·추첨·팀·OBS·종료도 기존 E2E 절차를 따릅니다.
